== Компиляция и выполнение кода C

Итак, у нас есть наша первая программа на языке C. Самое время попытаться выполнить ее и увидеть результат.

Язык C является *компилируемым* языком. Это означает, что написанный нами исходный текст на языке C не выполняется непосредственно. Сначала он должен быть преобразован в машинный код — набор инструкций, который может выполнить процессор. 

В этой главе мы подробно разберем путь, который проходит программа от исходного текста до исполняемого машинного кода. В качестве примера возьмем классический компилятор C из набора GCC (GNU Compiler Collection). 

=== Выбор компилятора

Из множества компиляторов C в качестве примера я выбрал GCC. Этот выбор не случаен. Он обусловлен несколькими причинами:

==== Свободное распространение и доступность

GCC (GNU Compiler Collection) — это свободное программное обеспечение с лицензией GPL. Это означает:

- **Бесплатность**: Любой студент, преподаватель или разработчик может установить GCC без каких-либо лицензионных ограничений
- **Кроссплатформенность**: GCC работает на Linux, Windows (через MinGW/MSYS2), macOS, BSD и многих других системах
- **Открытый исходный код**: При желании можно изучать, как работает сам компилятор

==== Стандарт де-факто в мире Unix/Linux

В экосистеме Linux и Unix-подобных систем GCC является основным компилятором:

- Ядро Linux компилируется с помощью GCC
- Большинство дистрибутивов Linux используют GCC по умолчанию
- Значительная часть инфраструктуры open-source проектов построена вокруг GCC

Изучая GCC, вы изучаете инструмент, который используется в реальной индустрии.

==== Образовательная ценность

GCC имеет богатую историю (первая версия выпущена в 1987 году) и хорошо документирован:

- **Подробная документация**: Официальные мануалы, туториалы, книги
- **Прозрачность работы**: Можно увидеть все этапы компиляции (препроцессинг, компиляция, ассемблирование, компоновка)
- **Богатый набор флагов**: GCC предоставляет управляемый флагами доступ ко всем фазам компиляции, что идеально для обучения

==== Совместимость со стандартами

GCC строго следует стандартам языка Cfootnote:[С использованием соответствующих флагов. Кроме того, в GCC имеется множество полезных расширений, многие из которых впоследствии входят в стандарт языка.]:

- Поддерживает C89/C90, C99, C11, C17, C23footnote:[Начиная с GCC 12; в GCC 15 поддержка C23 практически полная.]
- Имеет флаги для строгого соответствия стандартам (`-std=c11`, `-pedantic`)
- Предоставляет предупреждения о нестандартном коде (`-Wall`, `-Wextra`)

==== Экосистема инструментов

GCC — это не просто компилятор, а часть большой экосистемы GNU:

- **Binutils**: `as` (ассемблер), `ld` (линкер), `objdump`, `objcopy`, `nm`, `readelf`
- **GDB**: Отладчик, тесно интегрированный с GCC
- **Make**: Система сборки, которая работает с GCC "из коробки"

==== Применение в embedded

GCC реализован в множестве разных платформ, в том числе используемых во встраиваемых системах:

- **ARM GCC** (`arm-none-eabi-gcc`) — для микроконтроллеров ARM
- **AVR GCC** — для микроконтроллеров AVR
- **RISC-V GCC** — для архитектуры RISC-V
- **MIPS GCC**, **SPARC GCC** и другие

==== Возможные альтернативы

помимо GCC, существуют и другие компиляторы C.

===== Clang/LLVM

* **Преимущества**: Быстрее компилирует, лучше сообщения об ошибках, модульная архитектура
* **Недостатки**: Меньше флагов оптимизации для специфичных архитектур
* **Использование**: macOS (по умолчанию), FreeBSD, некоторые embedded проекты
* **Совместимость**: В большинстве случаев полная замена GCC (те же флаги)

===== MSVC (Microsoft Visual C++)

- **Преимущества**: Лучшая интеграция с Windows, отладчик Visual Studio
- **Недостатки**: Только под Windows, проприетарный, отличается синтаксис некоторых расширений
- **Использование**: Разработка под Windows
- **Особенности**: Другой синтаксис для некоторых pragma, другой формат объектных файлов (PE/COFF)

===== Intel C++ Compiler

- **Преимущества**: Оптимизация для процессоров Intel
- **Недостатки**: Платный, одноплатформенный (Intel), специфичные оптимизации
- **Использование**: Высокопроизводительные вычисления (HPC)

===== Коммерческие компиляторы для embedded

- **IAR Embedded Workbench**, **Keil MDK**, **Green Hills MULTI**
- **Преимущества**: Специализированные оптимизации, поддержка конкретных микроконтроллеров
- **Недостатки**: Очень дорогие, проприетарные, отсутствуют версии для PCfootnote:[Возможность генерации кода для PC весьма важна при тестировании кода, посколькку позволяет выполнять множество тестов непосредственно на компьютере разработчика]

===== Заключение

Мы используем GCC, потому что это:

- Бесплатный и доступный инструмент
- Стандарт индустрии для Linux и поддержка многих платформ embedded
- Образовательный инструмент с прозрачной работой
- Часть экосистемы GNU

Однако принципы, которые мы будем рассматривать дальше, **универсальны** и применимы практически к любому компилятору C. Различаются только конкретные флаги командной строки и названия некоторых артефактов.

=== Фазы компиляции

Процесс преобразования исходного кода в исполняемый файл в GCC традиционно делится на четыре основные фазы. Рассмотрим их на примере нашей простой программы `hello_world.c`, состоящей из единственного файла.

==== Препроцессор

Первым в игру вступает *препроцессор*. Он обрабатывает макродирективы (макросы), начинающиеся с литеры `#` (например, `#include`, `#define`, `#ifdef`):

* Раскрывает макросы (заменяет обращение к макросу на его содержимое, указанное в определении макроса).
* Подставляет содержимое заголовочных файлов вместо директив `#include`, как если бы сам разработчик скопипастил этот текст в свой код.
* Удаляет комментарии. Компилятор их даже не увидит.
* Обрабатывает условную компиляцию (удаляет код, для которого не выполняются определенные истории).

Язык макросов слишком сложен, чтобы описать его в этом разделе. Поэтому позднее мы рассмотрим его более подробно, а сейчас ограничимся минимумом для понимания общей картины.

Обычно результат работы препроцессора не виден программисту, он сразу же передается по цепочке дальше. Но при желании можно завершить компиляцию на этом этапе и рассмотреть, как выглядит обработанный препроцессором код. Иногда это нужно, когда разработчик перемудрил со слишком сложными макросами и хочет разобраться, что же происходит на самом деле. Также полезно посмотреть на обработанный код, чтобы лучше понять все происходящее при компиляции.

Чтобы остановить компиляцию на этапе препроцессора и получить результат его работы, используется флаг `-E`:

[source,bash]
----
gcc -E hello_world.c -o hello_world.i
----

Файл `hello_world.i` будет содержать уже обработанный препроцессором код на языке C, готовый к компиляции.

==== Компиляция

На этом этапе компилятор анализирует синтаксис обработанного препроцессором кода, строит абстрактное синтаксическое дерево (AST), проводит оптимизации и переводит код с языке C в **ассемблерный код** для целевой архитектуры.

Мы можем остановить компиляцию на этом шаге и посмотреть результат. Для этого воспользуемся флагом `-S`:

[source,bash]
----
gcc -S hello_world.i -o hello_world.s
----

Файл `hello_world.s` содержит текстовое представление инструкций процессора, на котором будет выполняться программа (например, x86_64 или ARM).

==== Ассемблирование

Ассемблер переводит текстовый ассемблерный код, полученный в результате компиляции, в **объектный файл**.

Объектный файл содержащий машинный код, но он еще непригоден для выполнения. Во-первых, все адреса в нем  заданы относительно некоторой начальной точки. Во-вторых, в нем отсутствует код из библиотек, которые мы включили посредством `#include`. Вместо этого в нем присутствует таблица символов, посредством которой мы можем использовать код из внешних модулей и код из внешних модулей может использовать наш, и некоторые метаданные для компоновки.

Флаг `-c` говорит GCC ассемблировать код, но не выполнять компоновку:

[source,bash]
----
gcc -c hello_world.s -o hello_world.o
----

==== Компоновка

Компоновщик (линкер) берет один или несколько объектных файлов, составляющих программу, а также использованные в ней библиотеки и объединяет их в единый *исполняемый файл*, разрешает внешние ссылки (связывает вызовы функций из других модулей с их реальными адресами в памяти) и формирует финальную структуру файла.

[source,bash]
----
gcc hello_world.o -o hello_world
----

Мы получили исполняемый файл `hello_world`.

==== Выполнение программы

Мы можем запустить нашу программу на выполнение:

[source,bash]
----
$./hello_world
Hello World!
----

Мы полностью прошли путь от исходного кода на C до исполняемого файла и получили вывод приветствия на консоль.

==== То же самое, но быстрее

Мы намеренно компилировали нашу первую программу неторопливо, по шагам, чтобы понять суть происходящих процессов и увидеть результаты кажждого из них. Тот же результат можно было получить быстрее, в одно действие:

[source,bash]
----
gcc hello_world.c -o hello_world
----

GCC последовательно выполнит все четыре фазы.

=== Независимая компиляция модулей

Одним из главных преимуществ языка C является возможность **независимой компиляции** (раздельной трансляции). Эта крайне полезная возможность предусмотрена не во всех языках. Например, классический Pascal требует, чтобы весь код программы находился в одном файле.

Программа на C может быть разделена между несколькими файлами. Это можно использовать для того, чтобы разбить сложную логику на несколько слабо зависящих друг от друга модулей меньшего размера, чтобы было проще их читать и редактировать.

Каждый файл `.c` вместе со всеми включенными в него заголовочными файлами образует **единицу трансляции** (translation unit). Компилятор обрабатывает каждую единицу трансляции независимо, не зная о существовании других файлов `.c` в проекте. Для связи между единицами трансляции нужны лишь заголовочные файлы `.h`? содержащие необходимые для компиляции объявления и определения (наподобие `stdio.h`).

[source,bash]
----
# Компилируем модули независимо друг от друга
gcc -c main.c -o main.o
gcc -c math_ops.c -o math_ops.o
gcc -c utils.c -o utils.o
----

Преимущества независимой компиляции:

* **Скорость сборки:** При изменении кода в `math_ops.c` нет необходимости перекомпилировать `main.c` и `utils.c`. Перекомпилируется только измененный модуль, после чего объектные файлы быстро перекомпоновываются. В больших проектах (миллионы строк кода) это экономит часы времени.
* **Модульность и инкапсуляция:** Функции, объявленные в `.c` файле без ключевого слова `extern` (или с `static`), не видны за пределами своей единицы трансляции (подробнее разберем далее). Это позволяет скрывать внутреннюю реализацию и при необходимости менять ее, не затрагивая структуру остальных модулей.
* **Повторное использование:** Скомпилированные объектные файлы или библиотеки можно использовать в других проектах без их исходного кода.

=== Использование библиотек

Когда независимых модулей становится много, их можно объединить в **библиотеки** для удобства. Библиотеки бывают двух основных типов: *статические* и *динамические*.

==== Статические библиотеки

Статическая библиотека (в Linux имеет расширение `.a`, в Windows `.lib`) — это просто набор объектных файлов (`.o`), собранных для удобства в один архив. Она создается с помощью утилиты `ar` (archiver):

[source,bash]
----
ar rcs libmath_ops.a math_ops.o utils.o
----

При компоновке исполняемой программы компоновщик берет из статической библиотеки *только те объектные модули*, которые необходимы для разрешения текущих внешних ссылок, и вставляет их машинный код напрямую в исполняемый файл.

Плюсы статических библиотек:

* Получаем монолитный исполняемый файл, который является самодостаточным.

Минусы:

* Если мы используем одни и те же библиотеки во многих программах, в каждую из них копируется один и тот же код. Это увеличивает необходимый для их хранения объем памяти.
* При внесении изменений в библиотеки необходимо заново собрать все программы, в которых они используются. Это особенно важно в случае, если изменения вносятся с целью исправления обнаруженных в ходе эксплуатации программы ошибок.

==== Динамические (разделяемые) библиотеки

Динамическая библиотека (в Linux `.so`, в Windows `.dll`) компилируется в отдельный бинарный файл. Машинный код библиотеки *не копируется* в исполняемый файл программы. Вместо этого при запуске программы загрузчик находит библиотеку в памяти или на диске и подгружает её в память, настраивая все ссылки на нее в соответствии с адресом загрузки.

Создание динамической библиотеки:

[source,bash]
----
gcc -shared -fPIC math_ops.o utils.o -o libmath_ops.so
----

Плюсы:

* Библиотечный код находится в отдельном от основной программы файле с исполняемым кодом, не увеличивая размер исполняемой программы.
* Можно изменять код динамической библиотеки (например, с целью оптимизации или исправления ошибок), не затрагивая исполняемый код основной программы.
* Некоторые готовые динамические библиотеки входят в состав ОС или доступны к загрузке от сторонних поставщиков. Их можно использовать как "черный ящик", не тратя время на разработку.
* Можно загружать динамические библиотеки в память при необходимости. Если в текущем сеансе работы какая-то функция не используется, она не будет загружена, тем самым не потребляя необходимые для ее работы ресурсы.

Минусы:

* Усложняется распространение двоичного кода программы. Помимо исполняемой программы, необходимо обеспечить наличие всех используемых разделяемых библиотек. Это может быть непростой задачей, особенно если разные программы используют разные несовместимые версии разделяемых библиотек.
* Нельзя использовать разделяемые библиотеки в прошивках для микроконтроллеров, поскольку весь исполняемый код должен быть загружен в постоянную память в процессе заливки программы.

[sidebar]
Флаг `-fPIC` означает Position Independent Code — позиционно-независимый код, необходимый для динамических библиотек.

==== Некоторые флаги GCC для работы с библиотеками

Чтобы скомпоновать программу, использующую библиотеки, GCC нужно указать, где искать заголовочные файлы и сами библиотеки:

`-I<путь>` (Include):: — указывает директорию для поиска заголовочных файлов (`#include`).
`-L<путь>` (Library):: — указывает директорию для поиска библиотек при компоновке.
`-l<имя>` (library):: — указывает имя библиотеки для компоновки. Имя пишется без префикса `lib` и расширения. Например, для `libmath_ops.a` флаг будет `-lmath_ops`.

Пример:

[source,bash]
----
# Компиляция с использованием заголовков из ./include и библиотек из ./lib
gcc main.c -I./include -L./lib -lmath_ops -o my_app
----

=== Полезные артефакты компиляции

В процессе компиляции генерируется множество промежуточных файлов. Каждый из них содержит информацию, которая может оказаться полезной в определенных условиях. Понимание этих артефактов помогает в отладке, оптимизации и анализе программы.

Далее вкратце описаны наиболее часто используемые артефакты компиляции, способы их получения и использования.

==== Объектный код

**Объектный файл** (обычно с расширением `.o` в Unix/Linux или `.obj` в Windows) — это бинарный файл, содержащий машинный код, сгенерированный компилятором из одной единицы трансляции (одного `.c` файла).

Объектный файл содержит:

*   **Машинный код** (инструкции процессора);
*   **Таблицу символов** (имена функций и глобальных переменных);
*   **Таблицу перемещений** (информация о ссылках на внешние символы, которые должны быть разрешены линкером);
*   **Секции** (код (`.text`), инициализированные данные (`.data`), неинициализированные данные (`.bss`) и другие);
*   **Отладочную информацию** (если компиляция проводилась с ключом с `-g`).

Получение объектного файла:

[source,bash]
----
# Компиляция в объектный файл
gcc -c module.c -o module.o

# Просмотр содержимого объектного файла
objdump -d module.o			# Дизассемблирование кода
nm module.o     			# Таблица символов
nm -u module.o				# Проверка неопределенных символов (внешних ссылок)
nm -u module.o				# Проверка неопределенных символов (внешних ссылок)
nm --defined-only module.o	# Проверка экспортируемых символов
readelf -a module.o         # Полная информация об ELF файле
objdump -h module.o         # Информация о секциях
----

==== Загрузочный модуль

**Загрузочный модуль** — это готовый к выполнению исполняемый файл, полученный после компоновки. В отличие от объектного файла, все внешние ссылки разрешены, и код готов к загрузке в память процессором.

Форматы загрузочных модулей:

**ELF** (Executable and Linkable Format)::
— стандарт для Linux и многих Unix-систем
**PE/PE32+** (Portable Executable)::
— формат для Windows
**Mach-O**::
— формат для macOS и iOS
**COFF** (Common Object File Format)::
— устаревший формат, предшественник PE

Получение загрузочного модуля:

[source,bash]
----
# Компоновка в исполняемый файл
gcc main.o module.o -o program

# Проверка типа файла
file program
----

Анализ загрузочного модуля:

[source,bash]
----
# Динамические зависимости (для ELF)
ldd program

# Информация о сегментах памяти
readelf -l program

# Информация о секциях
readelf -S program

# Размер секций
size program
----

==== Листинг компиляции

**Листинг** — это текстовый файл, содержащий исходный код программы вместе с сгенерированным машинным кодом. Это мощный инструмент для анализа того, как компилятор преобразует ваш код.

Получение листинга:

[source,bash]
----
# Генерация ассемблерного файла
gcc -S -O2 module.c -o module.s

# Просмотр содержимого
cat module.s
----

Для более наглядного анализа можно получить листинг, где исходный код на C чередуется с ассемблером:

[source,bash]
----
# Компиляция с генерацией смешанного листинга
gcc -c -g -Wa,-a,-ad module.c -o module.o > module.lst

# Или использование objdump
objdump -d -S -l module.o > module_mixed.lst
----

==== Карта памяти

**Карта памяти** (map file) — это текстовый файл, генерируемый линкером, который показывает, как различные модули и символы размещены в памяти итоговой программы.

Получение карты памяти:

[source,bash]
----
# Генерация map файла при компоновке
gcc main.o module.o -o program -Wl,-Map=program.map
----

Файл карты памяти содержит несколько важных секций:

. Распределение памяти
. Размещение секций
. Таблица символов
. Статистика использования памяти

Файл карты памяти помогает:

*   Найти, где размещены конкретные функции и переменные
*   Определить размер каждой секции
*   Выявить дублирование кода
*   Оптимизировать использование памяти
*   Найти "тяжелые" модули, занимающие много места

==== Файлы зависимостей

При использовании `make` или других систем сборки важно отслеживать, какие заголовочные файлы включены в каждый `.c` файл. Это позволяет перекомпилировать только те модули, которые действительно изменились.

Генерация файлов зависимостей:

[source,bash]
----
# Компиляция с генерацией файла зависимостей
gcc -MMD -MP -c module.c -o module.o
----

Файл `.d` содержит список всех файлов, от которых зависит объектный файл. При изменении любого из этих файлов необходимо перекомпилировать модуль.

==== Отладочная информация

При компиляции с флагом `-g` компилятор добавляет в объектный и исполняемый файлы отладочную информацию, позволяющую отладчику связывать машинный код с исходным кодом.

Форматы отладочной информации:

**DWARF** (Debugging With Attributed Record Formats)::
— стандарт для Unix/Linux
**PDB** (Program Database)::
— формат для Windows (MSVC)
**STABS**::
— устаревший формат

Получение отладочной информации^

[source,bash]
----
# Компиляция с отладочной информацией
gcc -g -O0 module.c -o module.o

# Извлечение отладочной информации
objdump --dwarf=info module.o > debug_info.txt
readelf --debug-dump=info module.o > debug_info.txt
----

Отладочная информация может зхначительно увеличить размер исполняемого файла. Для уменьшения его размера отладочную информацию можно вынести в отдельный файл:

[source,bash]
----
# Извлечение отладочной информации
objcopy --only-keep-debug program program.debug

# Удаление отладочной информации из исполняемого файла
strip --strip-debug --strip-unneeded program

# Добавление ссылки на файл отладки (для GDB)
objcopy --add-gnu-debuglink=program.debug program
----

==== Файлы покрытия кода

При тестировании программы можно собирать статистику покрытия кода — какие строки и ветки кода выполнялись во время работы программы.

Генерация файлов покрытия:

[source,bash]
----
# Компиляция с поддержкой покрытия кода
gcc --coverage -fprofile-arcs -ftest-coverage module.c -o module

# Это создаст файлы:
# module.gcno - содержит информацию о структуре программы (генерируется при компиляции)

# Запуск программы
./program

# После выполнения создаются файлы:
# module.gcda - содержит информацию о выполнении (генерируется при запуске)

# Генерация отчета о покрытии
gcov module.c
----

Файл `.gcov` содержит исходный код с пометками, какие строки выполнялись.

==== Препроцессированный код

Иногда полезно увидеть результат работы препроцессора — полностью раскрытый код со всеми макросами и включенными заголовочными файлами.

Получение препроцессированного кода:

[source,bash]
----
# Генерация препроцессированного файла
gcc -E module.c -o module.i

# Или с сохранением комментариев
gcc -E -C module.c -o module_with_comments.i
----

Препроцессированный файл может быть очень большим (десятки тысяч строк). Его имеет смысл создавать, если вы собираетесь:

*   Отлаживать сложные макросы
*   Разобраться, какие заголовочные файлы включены
*   Проанализировать результаты условной компиляции

=== Прочие полезные артефакты

==== Файлы промежуточного представления (IR)
Современные компиляторы используют промежуточное представление (Intermediate Representation) для оптимизации кода. Можно получить доступ к IR на разных этапах:

[source,bash]
----
# Генерация RTL (Register Transfer Language) для GCC
gcc -fdump-rtl-all module.c

# Генерация GIMPLE (высокоуровневое IR)
gcc -fdump-tree-gimple module.c

# Это создаст множество файлов с расширениями .c.*
----

==== Файлы профилирования
Для оптимизации производительности можно собирать профилировочную информацию:

[source,bash]
----
# Компиляция с профилированием
gcc -pg module.c -o module

# Запуск программы (создает файл gmon.out)
./program

# Анализ профилирования
gprof module gmon.out > profile.txt
----

==== Файлы санитайзеров
При использовании санитайзеров (AddressSanitizer, ThreadSanitizer и др.) генерируются отчеты о проблемах:

[source,bash]
----
# Компиляция с AddressSanitizer
gcc -fsanitize=address -g module.c -o module

# При запуске программы санитайзер выводит детальные отчеты о проблемах с памятью
----

=== Резюме

Артефакты компиляции — это не просто промежуточные файлы, а мощные инструменты для анализа, отладки и оптимизации программы. Объектные файлы содержат машинный код и метаданные для компоновки. Загрузочные модули готовы к выполнению. Листинги позволяют увидеть, как компилятор преобразует ваш код. Карты памяти показывают структуру итоговой программы. Файлы зависимостей ускоряют сборку. Отладочная информация связывает машинный код с исходниками. Понимание и использование этих артефактов — важный навык для любого разработчика на C.

=== Резюме раздела

Прошивка bare metal приложений требует дополнительного шага после компоновки — преобразования ELF файла в бинарный образ с помощью `objcopy`. Стартовый код на ассемблере обеспечивает инициализацию данных при запуске. Процесс прошивки может осуществляться через аппаратные программаторы (JTAG/SWD), встроенные загрузчики или системы самозагрузки. Контроль размера прошивки и оптимизация памяти являются критически важными задачами в разработке встраиваемых систем.
